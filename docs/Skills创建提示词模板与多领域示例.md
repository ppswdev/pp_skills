## 一、什么是创建 Skill 的提示词

所谓“创建 Skill 的提示词”，就是你给 AI 的一段说明，用来明确：

1. 你要创建什么 Skill
2. 这个 Skill 应该在什么场景下触发
3. 它要解决哪些问题
4. 它应该输出什么结果
5. 它在工作时要遵循哪些步骤、规则和边界

如果提示词写得足够清楚，AI 生成出来的 Skill 会更稳定、更容易复用，也更适合团队协作。

---

## 二、好提示词的核心结构

一个高质量的 Skill 创建提示词，建议至少包含以下 8 个部分：

### 1. Skill 名称与定位

说明这个 Skill 是做什么的，最好一句话讲清楚。

示例：

- 创建一个 `product-requirements-discovery` Skill，用于产品需求挖掘与需求澄清
- 创建一个 `sku-selection-analyst` Skill，用于电商选品分析和机会判断

### 2. 触发场景

说明用户会在什么情况下调用它。

示例：

- 当我需要把模糊想法整理成产品需求时调用
- 当我需要评估某个品类是否值得做时调用

### 3. 输入信息

说明 Skill 接收什么输入。

示例：

- 用户访谈纪要
- 市场数据
- 竞品链接
- PRD 草稿
- 仓库代码

### 4. 输出结果

明确 Skill 最终应该产出什么。

示例：

- 结构化需求文档
- 选品评分表
- 页面原型说明
- 技术实现方案
- 运营动作清单

### 5. 工作流程

描述 Skill 应该按什么顺序做事。

示例：

1. 识别目标与约束
2. 收集和整理输入信息
3. 建立分析框架
4. 输出结论与建议
5. 标记风险和待确认项

### 6. 规则与边界

告诉 AI 什么能做，什么不能做。

示例：

- 不要直接下结论，先列出假设
- 不要凭空编造市场数据
- 如果信息不足，明确列出待补充问题
- 输出尽量结构化，便于复制到文档系统

### 7. 输出格式

规定最终结果的展示方式。

示例：

- 使用 Markdown 输出
- 按“背景、问题、分析、建议、风险”结构输出
- 表格输出评分项

### 8. 示例请求

给出 3 到 5 个真实的触发语句，方便 Skill 更准确地匹配场景。

示例：

- 帮我把这些访谈内容整理成需求机会点
- 分析这个品类是否值得上架
- 基于这份 PRD 产出开发拆解方案

```markdown
当用户提出以下类型的需求时触发：
- [触发语句示例 1]

- [输入 1]
- [输入 2]
- [输入 3]

输出结果：
- [输出 1]

1. [步骤 1]

1. 完整的 SKILL.md 内容
2. 推荐的目录结构
3. 3 到 5 条可直接测试的用户示例指令
4. 如果有必要，请补充 references、scripts、assets 的建议
```

## 四、Skill 内容建议结构

当你让 AI 创建 Skill 时，建议它生成的 `SKILL.md` 至少包含以下内容：

```markdown
---
name: "skill-name"
description: "说明这个 Skill 在什么场景下使用，以及核心功能是什么"
---

# Skill 标题

## 适用场景

## 核心能力

## 输入说明

## 工作流程

## 输出要求

## 规则与边界

## 示例触发语句
```

如果这个 Skill 比较复杂，建议再拆分：

- `references/`：放行业知识、流程规范、分析框架
- `scripts/`：放重复执行、要求稳定的脚本
- `assets/`：放模板、表格、原型素材、文案素材

## 五、多领域创建示例

以下示例都可以直接复制给 AI，作为“创建 Skill”的原始提示词。

### 示例 1：产品需求挖掘 Skill

```markdown
请帮我创建一个 `product-requirements-discovery` Skill。

这个 Skill 用于产品需求挖掘，帮助我把零散的用户反馈、业务目标、访谈记录和竞品观察，整理成清晰的需求机会点与优先级建议。

适用场景：
- 我只有一些模糊想法，还没有形成正式需求
- 我拿到了用户访谈纪要，想识别真实痛点
- 我需要把老板/客户的口头需求整理成结构化输入
- 我想从反馈中发现高价值需求方向

触发方式：
当用户提出以下请求时触发：
- 帮我从这些访谈记录里挖掘需求
- 把这些用户反馈整理成产品机会点
- 帮我澄清这个需求到底要解决什么问题
- 根据这些信息输出需求洞察和优先级建议

输入信息：
- 用户访谈纪要
- 客诉记录或工单
- 社区评论
- 业务目标
- 竞品信息

输出结果：
- 需求背景总结
- 用户痛点清单
- 需求机会点列表
- 假设与待验证问题
- 优先级建议

工作流程要求：
1. 先梳理业务目标、目标用户和使用场景
2. 从输入中提取高频问题、强情绪点、重复需求和隐性需求
3. 区分“用户表达的方案”和“用户真实问题”
4. 归纳需求机会点，并按价值、紧急度、可行性进行排序
5. 输出结论时标记证据来源、假设项和待验证项

规则与边界：
- 不要把单个用户意见直接当成普遍需求
- 不要凭空补充不存在的用户证据
- 如果信息不足，要列出需要补充的调研问题
- 输出必须适合继续转化为 PRD

输出格式要求：
- 使用 Markdown
- 按“背景、用户、问题、机会、优先级、风险、待确认项”结构输出
- 机会点部分尽量用表格

请最终生成完整的 SKILL.md，并补充 5 条测试用示例指令。
```

### 示例 2：选品分析 Skill

```markdown
请帮我创建一个 `sku-selection-analyst` Skill。

这个 Skill 用于选品分析，帮助我评估某个品类、某个单品或某个市场机会是否值得进入，并输出结构化的判断和建议。

适用场景：
- 电商选品
- SaaS 产品方向筛选
- 新市场机会评估
- 利基品类机会判断

触发方式：
- 帮我分析这个品类值不值得做
- 评估一下这个产品方向的市场空间
- 根据竞品和用户需求做选品判断
- 帮我做一个进入与不进入的决策分析

输入信息：
- 平台销量数据
- 竞品价格带
- 用户评论
- 供应链信息
- 毛利测算
- 市场趋势信息

输出结果：
- 市场机会判断
- 竞争格局分析
- 用户需求与痛点分析
- 成本与毛利评估
- 风险点
- 是否进入的建议

工作流程要求：
1. 明确分析对象、目标市场和渠道
2. 评估市场需求强度、增长趋势和季节性
3. 分析竞品数量、价格带、卖点和评价缺口
4. 结合供应链、履约、成本、毛利做可行性判断
5. 输出进入建议、适合切入的人群和差异化方向

规则与边界：
- 信息不足时不要给出绝对结论
- 不要只看销量，必须结合竞争强度和利润空间
- 输出中要明确区分事实、推测和建议
- 如果数据质量较弱，要提醒结论可靠性有限

输出格式要求：
- 使用 Markdown
- 包含“结论摘要、市场、竞品、用户、利润、风险、建议”
- 对关键指标使用评分表

请最终输出完整 SKILL.md，并建议是否需要配套 `references/selection-framework.md`。
```

### 示例 3：产品设计 Skill

```markdown
请帮我创建一个 `product-design-planner` Skill。

这个 Skill 用于产品设计阶段，帮助我从需求出发，整理用户流程、信息架构、页面模块、交互逻辑和设计交付清单。

适用场景：
- 从 PRD 进入产品设计
- 需要梳理页面结构和用户路径
- 需要输出原型说明和设计说明
- 需要给设计师或前端明确交付边界

触发方式：
- 根据这份需求帮我做产品设计拆解
- 帮我整理这个功能的页面结构和交互流程
- 输出这个产品方案的原型说明
- 帮我把需求转成设计交付项

输入信息：
- PRD
- 用户故事
- 功能列表
- 竞品截图或参考链接
- 业务规则

输出结果：
- 目标用户与使用场景
- 用户流程图说明
- 信息架构建议
- 页面模块拆解
- 核心交互逻辑
- 设计交付清单

工作流程要求：
1. 先确认目标用户、使用场景和关键任务
2. 将需求拆成用户流程和任务路径
3. 提炼页面层级、模块关系和状态变化
4. 明确主流程、异常流程和边界场景
5. 输出设计交付清单，便于协作

规则与边界：
- 不要只罗列页面，要体现任务流转逻辑
- 必须考虑空状态、错误状态、加载状态
- 对不明确的规则要单独列出来
- 输出要能直接给 UI 设计师和前端继续使用

输出格式要求：
- Markdown 输出
- 按“目标、流程、页面、交互、状态、风险、交付项”组织
- 页面模块尽量列表化表达

请帮我产出完整的 SKILL.md，并补充 3 个适合放入 `references/` 的设计框架文件建议。
```

### 示例 4：产品开发 Skill

```markdown
请帮我创建一个 `product-development-executor` Skill。

这个 Skill 用于产品开发阶段，帮助我基于需求文档和现有代码仓库，输出技术拆解、开发计划、测试要点和交付建议。

适用场景：
- 需求进入开发前的技术评估
- 功能开发拆分
- 前后端协作任务划分
- 代码实现前的风险识别

触发方式：
- 根据这份 PRD 输出开发方案
- 帮我把这个功能拆成开发任务
- 分析这个需求在当前仓库里的实现方式
- 给我一个可执行的开发计划和测试清单

输入信息：
- PRD
- 技术栈说明
- 代码仓库
- 接口文档
- 数据库设计
- 非功能需求

输出结果：
- 技术实现思路
- 模块拆分建议
- 前后端任务清单
- 数据结构与接口影响点
- 风险与依赖
- 测试要点

工作流程要求：
1. 先理解业务目标和需求边界
2. 结合现有代码结构识别受影响模块
3. 给出技术实现路径和替代方案
4. 拆分为可执行的开发任务
5. 补充测试场景、回归范围和风险提示

规则与边界：
- 不要脱离现有仓库结构空谈方案
- 优先复用已有模块、模式和约定
- 如果存在不明确接口或数据规则，要明确标注
- 输出中要区分“必须做”和“建议优化”

输出格式要求：
- Markdown 输出
- 包含“背景、代码影响、方案、任务拆分、风险、测试”
- 任务拆分尽量细化到可执行级别

请最终生成完整 SKILL.md，并说明是否适合增加 `scripts/impact_scan.sh` 之类的辅助脚本。
```

### 示例 5：产品运营 Skill

```markdown
请帮我创建一个 `product-operations-planner` Skill。

这个 Skill 用于产品运营，帮助我围绕拉新、激活、留存、转化、召回等目标，制定运营分析框架和执行方案。

适用场景：
- 制定月度运营计划
- 设计活动方案
- 分析核心漏斗
- 提出留存和转化优化动作

触发方式：
- 帮我做这个产品的运营方案
- 设计一个提升激活率的运营动作清单
- 根据现有数据分析留存问题
- 产出一个活动策划和复盘框架

输入信息：
- 产品数据指标
- 用户分层信息
- 活动历史
- 渠道表现
- 产品版本信息
- 运营目标

输出结果：
- 目标拆解
- 漏斗问题定位
- 运营策略建议
- 活动方案框架
- 指标追踪建议
- 复盘模板

工作流程要求：
1. 先明确增长目标和评价指标
2. 分析当前漏斗、用户分层和关键问题
3. 输出对应的运营动作与优先级
4. 为每个动作补充适用人群、资源需求和预期指标
5. 最后输出复盘方式与监控建议

规则与边界：
- 不要只给泛泛建议，要尽量和目标指标绑定
- 不要忽略执行成本和资源约束
- 对没有数据支撑的结论要标注为假设
- 优先给出可落地动作，而不是空泛策略口号

输出格式要求：
- Markdown 输出
- 包含“目标、现状、问题、动作、指标、风险、复盘”
- 运营动作使用表格呈现

请输出完整 SKILL.md，并附带 5 条适合日常调用的示例语句。
```

## 六、常见问题与优化建议

### 1. 提示词太空，生成的 Skill 很泛

优化方法：

- 增加真实业务场景
- 增加触发语句示例
- 增加输入和输出定义
- 增加边界条件和禁止事项

### 2. Skill 能触发，但结果不稳定

优化方法：

- 把工作流程写成明确步骤
- 指定输出结构
- 区分“事实、假设、建议”
- 增加高质量示例请求

### 3. Skill 太长，维护成本高

优化方法：

- 把知识型内容拆到 `references/`
- 把重复执行逻辑拆到 `scripts/`
- `SKILL.md` 只保留核心流程和触发说明

### 4. 不知道该先做哪个领域的 Skill

建议优先级：

1. 高频重复任务
2. 团队协作中经常口径不统一的任务
3. 需要固定分析框架的任务
4. 对输出质量要求高、但流程相对稳定的任务

## 最后建议

如果你是要搭建自己的 Skill 仓库，建议按业务链路逐步沉淀：

1. 先做需求与分析类 Skill
2. 再做设计与开发类 Skill
3. 最后补充运营、复盘、国际化等扩展 Skill

这样更容易形成一套完整的方法论仓库，而不是零散工具集合。

你也可以继续追加一层分类目录，例如：

```text
skills/
├── opportunity/
├── strategy/
├── product/
├── research/
├── design/
├── engineering/
├── data/
├── growth/
├── sales/
├── monetization/
├── operations/
├── support/
├── finance-legal/
└── localization/
```
